## 1. なぜWebセキュリティを学ぶのか

```

├── 💰 金銭的損害：損害賠償、ビジネス機会の損失
├── 📉 信頼の失墜：顧客離れ、ブランドイメージの低下
├── ⚖️ 法的責任：個人情報保護法違反、GDPRなど
```

## 2. OWASP Top 10 とは

### 2.1 OWASPについて

**OWASP（Open Worldwide Application Security Project）**は、Webアプリケーションのセキュリティ向上を目的とした国際的なオープンコミュニティです。

**OWASP Top 10** は、Webアプリケーションにおける**最も重要なセキュリティリスク**のトップ10をまとめたものです。

### 2.2 OWASP Top 10 (2021年版)

| 順位 | カテゴリ | 概要 |
|------|---------|------|
| A01 | **アクセス制御の不備** | 権限のないリソースへのアクセス |
| A02 | **暗号化の失敗** | 機密データの不適切な保護 |
| A03 | **インジェクション** | SQL、OS、LDAPインジェクション等 |
| A04 | **安全でない設計** | 設計段階でのセキュリティ欠如 |
| A05 | **セキュリティの設定ミス** | デフォルト設定、不要機能の有効化 |
| A06 | **脆弱で古いコンポーネント** | 既知の脆弱性を持つライブラリ |
| A07 | **識別と認証の失敗** | パスワード管理、セッション管理の不備 |
| A08 | **ソフトウェアとデータの整合性の不備** | CI/CDの安全性、依存関係の検証 |
| A09 | **セキュリティログと監視の不備** | 攻撃の検知・対応ができない |
| A10 | **SSRF（サーバーサイドリクエストフォージェリ）** | サーバーからの不正なリクエスト |

## 3. 各リスクの解説

### A01：アクセス制御の不備（Broken Access Control）

最も多い脆弱性。**権限のないユーザーが、本来アクセスできないリソースにアクセスできてしまう**問題。

```
例1：URLの直接指定
/admin/users → 管理者画面に一般ユーザーがアクセスできてしまう

例2：パラメータの改ざん
/api/users/123/profile → IDを変えると他人のプロフィールが見れる
/api/users/456/profile → 他のユーザーのデータ！

例3：権限のエスカレーション
一般ユーザーが管理者権限の操作を実行できてしまう
```

```java
// ❌ 脆弱な実装
@GetMapping("/api/users/{id}")
public User getUser(@PathVariable Long id) {
    return userService.findById(id); // 誰のデータでも取得できる
}

// ✅ 安全な実装
@GetMapping("/api/users/{id}")
public User getUser(@PathVariable Long id, Authentication auth) {
    User currentUser = userService.findByUsername(auth.getName());
    if (!currentUser.getId().equals(id) && !currentUser.isAdmin()) {
        throw new AccessDeniedException("アクセス権限がありません");
    }
    return userService.findById(id);
}
```

**対策：**
- すべてのリクエストで認可チェックを行う
- デフォルトで拒否（deny by default）
- URLの直接アクセスを防ぐ
- サーバーサイドで権限検証を行う

### A02：暗号化の失敗（Cryptographic Failures）

**機密データが適切に暗号化されていない**問題。

```
よくある問題：
├── パスワードを平文で保存 → ハッシュ化すべき
├── HTTPで通信 → HTTPSを使うべき
├── 弱い暗号アルゴリズム → MD5, SHA-1は非推奨
├── 暗号鍵をソースコードに埋め込み → 環境変数で管理
└── 不要な機密データの保存 → 必要最小限に
```

```java
// ❌ パスワードを平文で保存
user.setPassword(rawPassword);

// ✅ BCryptでハッシュ化して保存
user.setPassword(passwordEncoder.encode(rawPassword));
```

### A03：インジェクション（Injection）

**ユーザー入力がそのままコマンドやクエリに組み込まれる**問題。（次回詳しく解説）

```sql
-- SQLインジェクションの例
-- ユーザーが入力: ' OR '1'='1
SELECT * FROM users WHERE name = '' OR '1'='1'  -- 全件取得されてしまう！
```

**対策：**
- パラメータ化クエリ（プリペアドステートメント）を使用
- 入力値のバリデーション
- ORM（JPA等）の活用

---

### A04：安全でない設計（Insecure Design）

**設計段階でセキュリティが考慮されていない**問題。

```
例：
├── パスワードリセットの質問が簡単に推測可能
├── レート制限がないAPI → ブルートフォース攻撃が可能
├── ビジネスロジックの欠陥
│   例：割引クーポンを無制限に使用できる
└── 適切なエラーメッセージの未設計
    例：「パスワードが間違っています」→ ユーザーの存在を漏らす
```

**対策：**
- 脅威モデリングの実施
- セキュアな設計パターンの採用
- レート制限の実装
- ビジネスロジックのレビュー

---

### A05：セキュリティの設定ミス（Security Misconfiguration）

```
よくある設定ミス：
├── デフォルトのアカウント/パスワードが残っている
├── 不要な機能やポートが有効
├── スタックトレースがユーザーに表示される
├── ディレクトリリスティングが有効
├── 適切なセキュリティヘッダーが設定されていない
└── CORSが適切に設定されていない
```

```
// ❌ 本番環境でスタックトレースを表示
HTTP 500
java.lang.NullPointerException
    at com.example.UserService.findById(UserService.java:42)
    at com.example.UserController.getUser(UserController.java:28)
    ...

// ✅ 適切なエラーメッセージ
HTTP 500
{"error": "Internal Server Error", "message": "予期しないエラーが発生しました"}
```

### A06：脆弱で古いコンポーネント（Vulnerable and Outdated Components）

```
問題：
├── 古いバージョンのライブラリを使用
├── 既知の脆弱性があるコンポーネント
├── OSやフレームワークのサポート切れ
└── 依存関係の把握ができていない

対策：
├── 依存関係を定期的に更新
├── 脆弱性データベースの監視（CVE, NVD）
├── 自動スキャンツールの導入
│   ├── Dependabot (GitHub)
│   ├── OWASP Dependency-Check
│   └── Snyk
└── 不要な依存関係の削除
```

---

### A07：識別と認証の失敗（Identification and Authentication Failures）

```
よくある問題：
├── 弱いパスワードの許可（"password", "123456"）
├── ブルートフォース攻撃への対策なし
├── セッション管理の不備
│   ├── ログアウト後もセッションが有効
│   ├── セッションIDの固定化攻撃
│   └── セッションタイムアウトが設定されていない
├── 多要素認証（MFA）の未実装
└── パスワードの平文保存
```

---

### A08：ソフトウェアとデータの整合性の不備

```
問題：
├── CI/CDパイプラインの安全性が確保されていない
├── 外部ライブラリの整合性を検証していない
├── 自動更新機能の署名検証なし
└── シリアライゼーションの安全でない利用

対策：
├── デジタル署名の検証
├── CI/CDの権限管理
├── 依存関係のハッシュ検証
└── 安全なシリアライゼーション
```

---

### A09：セキュリティログと監視の不備

```
問題：
├── ログイン失敗がログに記録されない
├── エラーや異常なアクセスが監視されていない
├── ログが適切に保護されていない
├── リアルタイムな検知・対応ができない
└── インシデント対応計画がない

必要なログ：
├── 認証イベント（成功・失敗）
├── アクセス制御の失敗
├── 入力バリデーションの失敗
├── アプリケーションエラー
└── 管理者操作
```

---

### A10：SSRF（Server-Side Request Forgery）

```
SSRFの仕組み：

ユーザー → アプリケーション → 内部サーバー（本来アクセスできない）

例：
POST /fetch-url
{"url": "http://internal-server:8080/admin"}
→ アプリケーションが内部サーバーにリクエストを送ってしまう
→ 内部ネットワークの情報が漏洩

対策：
├── URLのホワイトリスト
├── 内部ネットワークへのリクエストをブロック
├── ファイアウォールの設定
└── レスポンスの検証
```

## 4. セキュリティ対策の基本原則

### 4.1 多層防御（Defense in Depth）

```
┌─── ネットワーク：ファイアウォール、WAF ─────┐
│ ┌─── アプリケーション：入力検証、認証 ─────┐ │
│ │ ┌─── データ：暗号化、アクセス制御 ─────┐ │ │
│ │ │         重要なデータ              │ │ │
│ │ └──────────────────────────────────┘ │ │
│ └──────────────────────────────────────┘ │
└──────────────────────────────────────────┘
一つの防御が破られても、次の防御層がある
```

### 4.2 セキュアコーディングの原則

| 原則 | 説明 |
|------|------|
| **入力を信用しない** | すべてのユーザー入力を検証する |
| **最小権限の原則** | 必要最低限の権限のみ付与する |
| **デフォルトで拒否** | 明示的に許可されたものだけ許可する |
| **多層防御** | 一つの対策に頼らない |
| **フェイルセーフ** | エラー時は安全な状態にフォールバックする |
| **シンプルに保つ** | 複雑なロジックは脆弱性の温床になる |
